# GL Audit Engine — Forensic Accounting Design

**Module:** `ledger/auditor.py`  
**Class:** `GLAuditor`

---

## 1. Forensic Principles

The GL Audit Engine applies forensic accounting best practices to the General Ledger.
The goal is **precision diagnosis** — not just detecting problems, but tracing each
finding to the minimal set of source records responsible and explaining *why*.

### 1.1 Core Forensic Principles Applied

| Principle | Implementation |
|---|---|
| **Precision Matching** | Every finding cites exact `tID` and `tDB` so the operator can open the source record directly |
| **Minimal Explanation** | For balance diffs, the engine searches for the *smallest subset* of rows that sum to the exact discrepancy (`_subset_summing_to`) |
| **Counter-Entry Verification** | Before flagging a single-sided account, the engine proves no double-entry counterpart exists via two independent methods |
| **Extended Equation** | Uses `A = L + E + (Inc − Exp)` for open periods — avoiding false positives from net income that hasn't been closed to Equity |
| **Orphan Detection** | `srcTID == tID` signals a direct-posted entry (no `toDoubleEntry` pair) — the primary forensic indicator for unexplained balances |
| **Consistent Evidence** | All `affected` records carry the same fields: `acct, aType, amt, dt, desc, tID, srcTID, tDB` |

## 2. Checks and Their Forensic Logic

### 2.1 TB_IMBALANCE — Trial Balance Out of Equilibrium
- **Condition:** Σ Debit ≠ Σ Credit
- **Severity:** error
- **Forensic value:** This is the most basic integrity check. If the TB is imbalanced,
  all downstream checks are suspect. Fix this first.
- **Output:** Per-acctType breakdown showing which account class contributes to the diff.

### 2.2 ACCT_EQUATION — Accounting Equation
- **Condition:** `Assets ≠ Liabilities + Equity + (Income − Expenses)`
- **Severity:** error  
- **Key insight:** The *extended* equation is used for pre-closing periods.  
  Net Income (Income − Expenses) is part of the equation until year-end close.  
  `A − (L + E) = Net Income` is **normal**, not an error.  
  Only fails if there are mis-classified accounts whose acctType is not in the
  5 standard types — meaning the row contributes to no side of the equation.
- **Forensic:** `_subset_summing_to` finds the smallest set of bad-type rows that
  explain the exact diff. Affected list is sorted by `abs(amt)` descending.

### 2.3 ESCROW_IMBALANCE — Escrow Clearing Account
- **Condition:** `Acct.Cash.Escrow` net balance ≠ $0.00
- **Severity:** error
- **Forensic:** Escrow is a staging/clearing account. Every property purchase
  routes cash through it and it must zero out after all lines are posted.
  
  **Orphan detection:** A row is "orphan" when `srcTID == tID`. This means:
  - The row was direct-posted (e.g., from a bank statement import)
  - It was NOT generated by `toDoubleEntry()` as a counter-entry to a ledger record
  - It has no automatic counterpart

  **Suspect isolation:** The engine first tries `_subset_summing_to(orphans, balance)`.
  If orphans alone don't explain the diff, it tries the full escrow set.
  Only rows in the explaining subset are shown in `affected`.

### 2.4 DUP_TXN — Duplicate Transactions
- **Condition:** `Status == '⚠ Dup'` (set by `mergeGL(resolve_dups=False)`)
- **Severity:** error
- **Forensic:** Same `tID` appearing in multiple source DBs (e.g., both `llcAssets` and
  `llcExpRev`). Usually caused by a transaction entered manually and then imported via Agent.
- **Auto-apply:** Yes — removes all but the first occurrence.

### 2.5 ZERO_AMT — Zero-Amount Entries
- **Condition:** `abs(amt) < 0.01` on non-COA rows
- **Severity:** warning
- **Forensic:** Null/template rows. Often left over from DB initialisation.
- **Auto-apply:** Yes — safe to remove.

### 2.6 UNCLASSIFIED / BAD_ACCT_TYPE — Account Classification
- **Condition:** `acctType` empty or not in standard set
- **Severity:** warning
- **Forensic:** The COA lookup (`llcCOA._Type`) converts an `acct` path to one of:
  `Asset, Liability, Equity, Income, Expense, Staging`. If it returns `Bad_<acct>`,
  the account path is not in the COA. This causes accounting equation failures.
- **Fix:** Correct the `acct` field in the source DB to match a valid COA entry.

### 2.7 SINGLE_SIDE — Single-Sided Entries Without Counter-Entry
- **Condition:** Account has entries on only one side (all Debit or all Credit)
  **AND** no double-entry counterpart can be confirmed
- **Severity:** warning
- **NOT flagged if:** A counter-entry exists — even in a different account.
  Many accounts are legitimately one-sided in isolation (e.g., `Acct.Exp.Operating`
  only carries Debits, but each Debit has a Credit counterpart in `Acct.Cash.Escrow`
  or `Acct.Cash.Bank`). These are correct double-entry pairs.

  **Counter-entry detection (two strategies):**
  1. **srcTID index** (authoritative): `toDoubleEntry()` stamps both the primary and
     counter entry with `srcTID = original_tID`. If another GL row shares the same
     `srcTID` but uses a different `acct`, the counter exists.
  2. **tID sign-flip**: Credit entries carry negative signed amounts in their tID
     (`date_-amt.xx`); Debit entries carry positive (`date_+amt.xx`). Look for the
     matching opposite-signed tID in the GL.

  **Root cause indicator:** `reason='orphan: srcTID=tID'` means the source record
  had `Ledger=nan` or blank — preventing `toDoubleEntry()` from generating a counterpart.

## 3. Audit Summary Chips (UI)

The GL view banner and audit summary panel show two chips:

| Chip | Meaning |
|---|---|
| `✅ Clean` / `N errors, M warnings` | Overall audit status |
| `✅ A = L+E` | Accounting equation holds (extended form, including Net Income) |
| `❌ A ≠ L+E` | Accounting equation fails for reasons beyond open-period Net Income |

---

## 4. tID / srcTID Conventions

These are critical for forensic tracing:

| Field | Value | Meaning |
|---|---|---|
| `tID` | `date_+amt.xx` | Debit entry (positive signed amount) |
| `tID` | `date_-amt.xx` | Credit entry (negative signed amount) |
| `srcTID` | different from `tID` | Generated by `toDoubleEntry()` from a source record with `tID=srcTID` |
| `srcTID` | same as `tID` | Direct-posted entry — orphan, no double-entry pair |
| `srcTID` | empty | COA seed row or legacy record without tracking |

**Formula:** `toTid(r) = f"{r['dt']}_{toKAmt(r):.2f}"` where `toKAmt` returns negative amount for Credits.

## 5. Accounting Equation: Open vs Closed Period

**Pre-year-end close (open period):**
```
Assets = Liabilities + Equity + (Income − Expenses)
```
Income and Expense accounts are still active. Net Income has not been closed to Retained Earnings.

**Post year-end close:**
```
Assets = Liabilities + Equity
```
Income/Expense zeroed out; Net Income transferred to Equity via closing journal.

The audit engine always uses the *open period* form. `A − (L+E) = Net Income` is expected and not flagged as an error.

## 6. Subset-Sum Forensics (`_subset_summing_to`)

When a balance discrepancy exists, finding *which* transactions caused it is a
subset-sum problem. The engine uses brute-force enumeration for small sets (≤20 rows):

```python
for size in range(1, len(rows)+1):
    for combo in combinations(rows, size):
        if abs(sum(signed_amt(r) for r in combo) - target) < 0.01:
            return list(combo)   # minimal exact explanation found
```

This guarantees the *smallest* set of rows whose signed amounts explain the diff exactly.
For sets >20 rows, falls back to showing all candidate rows.

## Lessons Learned — Session 2026-06-02

### Accounting
- **Open-period BS equation is A = L + E + NI**: Revenue/Expense accounts remain open for K-1 detail in LLC partnerships. The `A − (L+E) = NI` gap on the Balance Sheet is expected and correct — not a bug. Only flag it as an error if the gap does NOT equal the Income Statement net income.
- **BSAuditAgent verdict `open_period_ni`**: When the BS gap exactly matches NI from the income statement, the correct audit verdict is `open_period_ni` (informational), not an equity error. This distinction avoids false-positive alerts for operators.
- **YE closing entries break the open-period equation**: After posting `Dr Acct.Equity.Earnings.PnL / Cr Acct.Equity.Owner.Capital.Funds`, the income/expense accounts zero out and the standard `A = L + E` equation holds. The audit engine should detect which regime it's in (open vs closed) and apply the matching equation.

### Software Engineering
- **BSAuditAgent belongs in the Actions menu, not the GL view**: The Balance Sheet audit is a separate action triggered by the user, not an inline GL warning. Surfacing it in the Actions menu (alongside YE Closing) keeps the GL view focused on transaction-level findings.
- **Extended equation must tolerate acctType=Staging**: Escrow and clearing accounts tagged `Staging` must be excluded from all five sides of the accounting equation (`A, L, E, Inc, Exp`) or the equation will appear to fail for correct ledgers with active escrow balances.
- **`_subset_summing_to` performance cap at 20 rows is correct**: Above that threshold the combinations count is O(2^N); returning all candidate rows is the right fallback rather than blocking the UI with a long computation.
